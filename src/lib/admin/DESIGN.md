# 管理后台服务设计

## 设计目标

为管理后台提供可审计的内容、用户角色和分类维护闭环，同时保持公开浏览和统一上传流程不变。

## 方案选择

后台采用 Next.js Server Components 查询数据、Server Actions 执行变更。作品的跨表编辑使用 Supabase 事务 RPC；没有新增管理专用上传入口，编辑器新增图片继续复用现有 R2 预签名上传接口。

## 关键决策

- 页面加载和每个 Action 都重新调用 `requireAdmin()`，界面按钮不作为权限边界。
- 超级管理员仍使用 `admin` 角色访问后台；只有唯一的 `is_super_admin` 可以调整其他用户角色，超管自身不可降级。
- `admin_list_users()` 与 `admin_set_user_role()` 因需要访问 Auth 邮箱或受保护角色列而使用 `SECURITY DEFINER`；只向 `authenticated` 开放，函数入口分别再次校验管理员和唯一超管，参数化查询且固定空 `search_path`。这是经过审计的受控例外。
- 搜索词、页码、状态和作品 UUID 在服务端约束后再进入查询。
- 单条作品保存由 `admin_update_prompt()` 在一个数据库事务中更新作品、图片、标签和验证平台。
- 删除单图先在客户端暂存，可撤销；数据库保存成功后才清理 R2。至少保留一张图片。
- 新图片只能使用当前管理员上传前缀；已有导入图片允许保留，但数据库统一限制在 `prompts/` 安全目录并拒绝路径穿越。
- 分类和标签的 key 保持不可变；仍有公开内容使用时不能停用。
- 上下架后通过 `updateTag("prompts")` 刷新公开内容缓存。
- 永久删除要求完整 R2 写入配置，先删除 Supabase 记录，再清理 R2 图片。
- 操作后的返回地址只允许 `/admin` 及其子路径，避免开放重定向。

## 已知限制

- Supabase 与 R2 不支持跨服务事务；数据库删除成功而 R2 清理失败时会留下孤儿对象，并向管理员显示人工检查提示。
- 当前没有批量操作、举报审核、用户封禁/删除、完整业务统计和自动化孤儿对象清理。
- 项目尚未引入单元测试框架，当前通过类型、Lint、生产构建、安全扫描和浏览器检查验证。

## 变更历史

### 2026-08-21 - 扩展为模块化管理后台

新增总览、用户管理、分类管理和指定作品编辑；支持单张图片排序、替代文本、暂存移除与保存后清理，同时将角色调整限制为唯一超级管理员。

### 2026-08-06 - 建立第一版内容管理模块

新增作品搜索、状态筛选、分页、上下架与永久删除，并将管理员角色校验集中到服务端授权模块。
